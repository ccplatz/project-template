# Parallel Worktree Stacks Design

## Context

The shared `bin/worktree` tooling currently models one active Worktree and one
Sail stack. It stores one name in `.worktree-active`, uses one Compose project
name, gates every stack on host port `8080`, and invokes Compose with
`--remove-orphans`. This makes switching worktrees destructive when another
stack is still needed.

The template must support multiple independent Laravel Sail stacks by default.
The change applies to the reusable template tooling only. Consumer-owned
Compose files, container user mappings, existing root-owned files, and
Playwright configuration are integration concerns for each consumer project.

## Goals

- Run multiple Worktree stacks concurrently without cross-stack container,
  volume, network, or port interference.
- Make the HTTP URL and all managed host ports explicit and reproducible.
- Preserve convenient commands that operate on the selected Worktree while
  allowing every stack to be addressed by name.
- Make stale selection and per-Worktree state recoverable instead of fatal.
- Make Worktree bootstrap resumable after dependency installation failures.
- Keep the implementation testable with the existing Bash test seam.

## Non-Goals

- Adding or generating a consumer's `compose.yaml` or `docker-compose.yml`.
- Changing consumer-owned Compose service definitions or adding a `user:`
  mapping to them.
- Repairing files that were previously created as root inside a consumer.
- Implementing consumer-specific Playwright base URLs or E2E project names.
- Supporting arbitrary, undiscovered host-port mappings beyond the standard
  Worktree port contract in the initial implementation.

## Session Boundaries

The implementation is deliberately split into two dependent sessions.

### Session 1: Parallelization Foundation

This session implements the per-Worktree identity and lifecycle model:

- Compose project names per Worktree.
- Persisted port groups and collision-safe allocation.
- Addressable `start`, `stop`, and `status` commands.
- Non-destructive `switch` behavior.
- Stale-state reporting and pruning.
- Regression tests and shared Worktree documentation.

This session addresses P0, P1, P6, P8, and P9 from the incident report.

### Session 2: Bootstrap and Validation Lifecycle

This session builds on the isolated identity model:

- Resumable `bootstrap <name>` command.
- Target-only cleanup when the target stack cannot start.
- Keeping the target stack alive when Composer, npm, or key generation fails.
- Compose file discovery and preflight validation.
- Regression tests for partial bootstrap and missing Compose files.

This session addresses P2, P5, and P7 from the incident report.

## State Model

`.worktree-active` remains an ignored selection pointer for commands without an
explicit Worktree name. It no longer identifies the only valid running stack
and it must never be used to decide which other stack to stop.

Per-Worktree state is stored below the already ignored `.worktrees` directory:

```text
.worktrees/.state/<name>.env
```

The state file is generated by the tooling, written atomically, and contains
validated values at least equivalent to:

```text
WORKTREE_NAME=readings-filters
COMPOSE_PROJECT_NAME=consumption-readings-filters
APP_PORT=8080
VITE_PORT=5173
FORWARD_DB_PORT=3306
FORWARD_REDIS_PORT=6379
```

The exact allocated values are persisted and reused on every later start. The
state directory is not committed and needs no additional `.gitignore` entry
because it is below `.worktrees`.

If a Worktree has no state file, the first explicit `start` or `bootstrap`
allocates and persists one. Existing `.env` values may be adopted only when
they form a complete, valid, unclaimed standard port group; otherwise a fresh
group is allocated. An old stack using the legacy project name is not adopted
implicitly. The migration documentation must tell the user to stop that old
stack before choosing its ports for the new state model.

State for a removed Worktree is reported as orphaned. A `prune` command may
remove only state whose Worktree path and Git worktree entry no longer exist.
Pruning must never stop or remove Docker containers.

## Compose and Port Isolation

Each named Worktree uses a project name derived from the validated base project
name and Worktree name:

```text
<PROJECT_NAME>-<worktree-name>
```

The Worktree name validation already limits the allowed characters. The
implementation must additionally validate the resulting Compose name before
using it.

The initial standard port contract contains:

- `APP_PORT` for the HTTP endpoint.
- `VITE_PORT` for the Vite development server.
- `FORWARD_DB_PORT` for the database host mapping.
- `FORWARD_REDIS_PORT` for the Redis host mapping.

The allocator assigns a complete port group, checks both persisted reservations
and actual host availability, and holds a short atomic allocation lock while
selecting and writing a group. It must not reuse a group reserved by another
Worktree even when that stack is currently stopped. If no group is available,
the command fails without starting Compose.

For allocation group index `n`, starting at zero, the standard ports are
calculated as follows:

```text
APP_PORT            = 8080 + (n * 10)
VITE_PORT           = 5173 + (n * 10)
FORWARD_DB_PORT     = 3306 + (n * 10)
FORWARD_REDIS_PORT  = 6379 + (n * 10)
```

The allocator selects the first group whose complete port set is both
unreserved and available on the host. Port `80` is never an implicit fallback
for Worktree-managed HTTP access.

Every Compose/Sail invocation for a Worktree loads its state and passes the
stored project name and port variables together with `SAIL_SOURCE_PATH` and the
appropriate `SAIL_BIN`. `--remove-orphans` is therefore scoped to the unique
Compose project name and cannot classify another Worktree's containers as
orphans.

The command output must show the Compose project name, HTTP URL, and complete
standard port group so the target is unambiguous:

```text
project: consumption-readings-filters
url: http://127.0.0.1:8080
ports: app=8080 vite=5173 db=3306 redis=6379
```

Consumer Compose files must use the standard variables in their host-port
mappings. Additional consumer-specific forwarded ports are outside the first
port profile and must not be silently guessed by the shared tooling.

## Command Semantics

The public command shape becomes:

```text
bin/worktree create <name> [--existing]
bin/worktree bootstrap <name>
bin/worktree start [<name>] [--fresh]
bin/worktree stop [<name>]
bin/worktree switch <name> [--fresh]
bin/worktree status [<name>]
bin/worktree status --all
bin/worktree prune
```

- `start`, `stop`, and `status` without a name use `.worktree-active`.
- A missing or stale selection produces a clear diagnostic and does not block
  commands that specify a valid name.
- `switch` selects and starts the target but never stops a previously running
  Worktree.
- `stop <name>` stops only that Worktree's Compose project.
- `status --all` reports running, stopped, and orphaned Worktree state.
- `prune` removes only orphaned state and does not alter Git worktrees or
  Docker resources.
- `create` validates prerequisites, creates the Git Worktree, allocates state,
  and invokes `bootstrap`. The selection pointer is updated only after a
  successful bootstrap.
- A failed `create` leaves the Worktree and state available for explicit
  `bootstrap <name>`; it does not overwrite the previous selection.
- `--fresh` updates the selection only after the target starts and the
  requested database reset succeeds. A failed reset leaves the target running
  and preserves the previous selection.

## Bootstrap Lifecycle

Bootstrap is an idempotent sequence whose successful artifacts are checked
before rerunning a step:

1. Ensure the target `.env` exists.
2. Ensure a supported Compose file exists.
3. Allocate or load the target state.
4. Start only the target stack.
5. Install Composer dependencies through the running target stack.
6. Verify the target Sail executable and use it for npm installation.
7. Generate the application key only when it is empty.

If the target stack cannot start, the tooling may attempt to bring down only
that target project because its Compose name is isolated. The target Worktree
and state remain for retry.

If Composer, npm, or key generation fails, the target stack remains running.
The command reports the failed step and the exact `bootstrap <name>` retry.
The previous selection and every other running Stack remain untouched.

The validation accepts Docker Compose's standard discovery names, including
`compose.yaml`, `compose.yml`, `docker-compose.yml`, and
`docker-compose.yaml`. The tooling never creates a symlink or generated
Compose file. If none exists, validation fails before a stack is started.

## Stale State and Recovery

State resolution must distinguish these cases:

- The selection file is absent: commands requiring an implicit target explain
  how to choose one explicitly.
- The selection names a removed Worktree: `status` reports it as stale rather
  than aborting with an internal resolution error; named commands continue to
  work.
- A per-Worktree state file exists but its Worktree is gone: `status --all`
  reports it as orphaned and `prune` can reclaim the reservation.
- A state file is malformed or has conflicting ports: the command fails closed
  with the Worktree name and state path, instructs the user to stop that named
  stack, remove the invalid state file, and rerun `start <name>`; it must not
  start Compose with guessed values.

No stale-state path may cause an unrelated running Stack to be stopped.

## Testing Strategy

The existing shell seam in `tests/bin/worktree_test.sh` remains the primary
test mechanism. The mock Sail command records environment variables and
arguments; it must model separate Compose project names, port values, and
running-state markers.

Session 1 tests must cover:

- Two Worktrees receive distinct project names and port groups.
- Both stacks can start without a `8080` global gate.
- Starting, switching, or stopping one Worktree does not issue a stop/down for
  another Worktree.
- State values survive stop/start and are reused.
- Busy ports and reserved ports are not assigned twice.
- A stale selection does not prevent named `status`, `start`, `switch`, or
  `create` operations.
- `status --all` distinguishes running, stopped, and orphaned entries.
- `prune` removes orphaned state without invoking Docker or Git removal.
- Failed target startup cleans only the target project.

Session 2 tests must cover:

- `bootstrap <name>` can resume after partial Composer, npm, or key failure.
- Dependency failures leave the target stack running and do not restart or
  stop the previous stack.
- Repeated bootstrap does not discard already valid artifacts.
- All supported Compose filenames pass validation.
- Missing Compose files fail before `up` is invoked.
- A failed target `up` leaves the Worktree and state available for retry.

The standard validation remains the shell test suite, ShellCheck when
available, and `git diff --check`. Docker-backed tests are not required for the
template because consumer Compose files are outside its ownership.

## Documentation and Consumer Contract

Add template-owned Worktree documentation covering:

- the command syntax and non-destructive `switch` behavior;
- state-file location and stale-state recovery;
- the standard port variables and URL output;
- the requirement that consumer Compose files map those variables;
- first-use migration of a legacy single-stack Worktree;
- the fact that user mapping and E2E base URLs remain consumer-owned.

The documentation must use `http://127.0.0.1:<APP_PORT>` as the canonical
development URL and must not describe port 80 as an alternate Worktree URL.

## Acceptance Criteria

- Two named Worktrees can remain running simultaneously through
  `bin/worktree start <name>` without one stack removing another's containers.
- Every running Worktree has a unique Compose project name and persisted
  standard port group.
- The command output identifies the exact URL and project.
- Removing or corrupting the active selection does not make independent named
  Worktree commands unusable.
- A failed dependency bootstrap can be resumed without manually reconstructing
  the Worktree or restarting an unrelated stack.
- The existing shell tests and all new regression tests pass.
- No consumer-owned Compose, root ownership, or E2E behavior is changed by the
  template implementation.
